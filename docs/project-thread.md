# Project, Thread, and Section Operations

This document defines the Cypheria-owned operations for projects, threads, project membership, sections, and section membership. The relational schema, column types, constraints, and indexes are defined separately in the [Database Guide](database.md).

## Identities and shared inputs

Project, thread, and section identities are UUIDv7 values generated by Cypheria. The pinned section has the fixed identity:

```text
01984de2-8f74-7c91-a3b2-5c5e937cf318
```

Section membership uses a discriminated reference:

```ts
type SectionItemRef =
  | { type: "thread"; id: string }
  | { type: "project"; id: string }
```

Operation inputs and outputs expose timestamps as Unix timestamps in seconds. Service properties use camel case, including `agentSessionId`, `forkedFromId`, `recencyAt`, `createdAt`, and `updatedAt`.

## Ordered-list behavior

The global project list, global thread list, threads within each project, global section list, and mixed items within each section are independent ordered lists.

Callers never write raw positions. An ordered mutation accepts an optional `beforeProjectId`, `beforeThreadId`, `beforeSectionId`, or mixed `beforeItem`. Null or omission means append. A referenced item must exist in the destination list. A move before itself or to its existing effective location is an idempotent no-op.

Every ordered mutation runs in one database transaction and compacts each affected list to contiguous zero-based positions. Reordering a project or thread globally does not alter project or section membership order. Changing membership does not alter the entity's global order.

## Project operations

- `createProject({ name, roots, beforeProjectId?, sectionPlacement? })` generates a UUIDv7, inserts the project into the global project list, and optionally creates its section membership in the same transaction. A new project has null `recencyAt`.
- `getProject(projectId)` reads one project without implicitly expanding members or section state.
- `listProjects({ cursor?, limit?, sortKey?, sortDirection? })` supports `position` and `recencyAt`. Recency sorting always places null values last.
- `updateProject(projectId, { name?, roots? })` changes user-authored metadata only. It cannot write global position, section membership, or recency.
- `moveProject({ projectId, beforeProjectId? })` changes only the global project order.
- `deleteProject(projectId)` removes the project's project and section membership rows, preserves its threads, compacts affected lists, and deletes the project atomically.

## Thread operations

- `createThread({ agentId, forkedFromId?, title?, cwd?, recencyAt?, beforeThreadId?, projectPlacement?, sectionPlacement? })` generates a UUIDv7 and creates the thread plus optional project and section memberships atomically. Its reserved `agentSessionId` field is null.
- `getThread(threadId)` reads a thread by its Cypheria identity.
- `listThreads({ agentId?, projectId?, sectionId?, forkedFromId?, cursor?, limit?, sortKey?, sortDirection? })` supports global `position` and `recencyAt` ordering.
- `updateThread(threadId, { title?, cwd? })` changes user-authored metadata only. Agent identity, fork source, recency, positions, and memberships have dedicated semantics.
- `touchThreadRecency({ threadId, recencyAt })` advances thread recency monotonically and recomputes the current project's recency in the same transaction.
- `moveThread({ threadId, beforeThreadId? })` changes only the global thread order.
- `deleteThread(threadId)` removes its project and section memberships, lets the self-reference foreign key clear child `forkedFromId` values, compacts affected lists, recomputes its former project's recency, and deletes the thread atomically.

`agentId` and `forkedFromId` are immutable after thread creation. Association with an agent session is deliberately outside the current operation surface: no create-time binding, lookup by agent session, or bind/update operation is implemented yet.

## Project membership operations

- `getThreadProject(threadId)` returns the thread's single project membership, if any.
- `listProjectThreads({ projectId, cursor?, limit? })` returns threads in project-item order.
- `moveThreadToProject({ threadId, projectId, beforeThreadId? })` inserts, reorders, or moves the membership. Moving between projects compacts both lists and recomputes both project recencies atomically.
- `removeThreadFromProject(threadId)` removes the membership, compacts the former project, and recomputes its recency. Missing membership is an idempotent success.

Project membership does not affect section membership. A thread may belong to a project and independently appear in one section.

When a membership is first created, its `createdAt` and `updatedAt` use the current Unix second. Reordering inside the same project preserves `createdAt` and advances `updatedAt` for every row whose stored position changes. Moving to a different project begins a new membership lifetime, so both timestamps are reset.

## Section operations

- `ensurePinnedSection()` is an initialization-only idempotent operation that inserts or validates the fixed pinned section.
- `createSection({ name, icon?, color?, beforeSectionId? })` generates a UUIDv7 and inserts a normal section after the pinned section.
- `getSection(sectionId)` reads one section.
- `listSections({ cursor?, limit? })` returns sections in global section order, with the pinned section first.
- `updateSection(sectionId, { name?, icon?, color? })` updates a normal section. The pinned section's identity and name are immutable.
- `moveSection({ sectionId, beforeSectionId? })` reorders a normal section without changing its items. The pinned section cannot move, and a normal section cannot move before it.
- `deleteSection(sectionId)` rejects the pinned ID, removes only the section's membership rows, preserves referenced projects and threads, and compacts global section order.

## Section membership operations

- `getItemSection(item)` returns the thread or project's single section membership, if any.
- `listSectionItems({ sectionId, cursor?, limit? })` returns one ordered discriminated union of hydrated thread and project items.
- `moveItemToSection({ item, sectionId, beforeItem? })` inserts, reorders, or moves a thread or project. Threads and projects share the same section position domain, so `beforeItem` may be either kind. Moving between sections compacts both lists atomically.
- `removeItemFromSection(item)` removes the membership and compacts its former section. Missing membership is an idempotent success.
- `pinItem({ item, beforeItem? })` delegates to `moveItemToSection` with the fixed pinned section ID.
- `unpinItem(item)` removes membership only when the current section is pinned. It does not restore an earlier section because membership history is not stored.

When a section membership is first created, its `createdAt` and `updatedAt` use the current Unix second. Reordering inside the same section preserves `createdAt` and advances `updatedAt` for every row whose stored position changes. Moving to a different section begins a new membership lifetime, so both timestamps are reset.

## Recency invariant

A thread's `recencyAt` is null until it has meaningful activity. `touchThreadRecency` uses the greater of its current value and the supplied Unix second, so delayed events cannot move recency backwards.

A project's `recencyAt` is the maximum non-null `recencyAt` of its current member threads, or null when no member has recency. It is not directly writable. Creating, moving, or removing project membership, touching a member thread's recency, or deleting a member thread recomputes every affected project in the same transaction.
